# 9–18 August 2026

**Mars was away. The NUC was frozen for the entire period and the board
displayed it as green the whole time.** Nothing else was seriously wrong.

---

## The one thing that matters

The NUC died on 8 August at 19:05 and did not come back until Mars physically
unplugged it on the 18th. Full account in
[`docs/postmortems/2026-08-08-nuc-freeze.md`](../postmortems/2026-08-08-nuc-freeze.md).

The freeze is the boring part — hardware does that. **The monitoring is the
part that should sting:**

```
nuc   pass   last=2026-08-06T14:30:14   human browser (desktop+mobile) · desktop 200 8.48s
```

Status `pass`. Last run 6 August. Read on the 18th. **Twelve days stale and
still showing green**, because a worker that stops reporting keeps its last
status forever. The board had no concept of "this answer has expired".

The fleet's own council spotted it unprompted, and said it better than this
report can:

```
claude r1: `nuc` reads `pass` while being 231h stale — a browser check from
           2026-08-06 shown as green on 2026-08-16.
```

So the information was there. Nobody was reading the council output, which is
its own small lesson about where findings go to die.

## What was actually running

Not nothing — the Mac carried the whole period alone:

```
2026-08-09  357     2026-08-14  2994
2026-08-10  420     2026-08-15  275
2026-08-11  406     2026-08-16  352
2026-08-12  356     2026-08-17  393
2026-08-13  404     2026-08-18  178
```

Requests per day to the board. Steady ~350–400. Council ran on the 10th, 11th,
13th, 16th, 17th and 18th; the rota kept proposing throughout.

The 14 August spike was benign — one Firefox on Windows polling `/api/processes`
and `/workers.json` 1,194 times each. A dashboard left open in a tab, not an
attack.

## What broke and what it cost

| What | When | Cost |
|---|---|---|
| NUC hard freeze | 8 Aug 19:05 | 9 days of silence |
| Board showed stale worker as `pass` | Ongoing | The 9 days went unnoticed |
| OpenClaw gateway failed to restart | 8 Aug 23:03 | Mac Telegram bot silent overnight |
| `.venv311` lost its `bin/` | Unknown | 6 fleet services dead on reboot |
| pytest unrunnable | Same cause | A stale dependency hid for weeks |
| `localvoice` alerting | Since ~10 Aug | Still broken, still unfixed |

The gateway failure was separate and earlier. A config change triggered a
restart that never landed:

```
[2026-08-08T22:03:24Z] openclaw restart attempt source=launchd-handoff mode=reload
Bootstrap failed: 5: Input/output error
[2026-08-08T22:03:29Z] openclaw restart failed status=37
```

The service was fully unloaded from launchd, so its own `KeepAlive` could not
save it. Five of Mars's messages sat queued on Telegram's servers until the
9th.

## What was built

Four commits on main, all on 18 August, all repair rather than feature work.

**Two watchdogs on the NUC.** `iTCO_wdt` hardware watchdog with
`RuntimeWatchdogSec=30s` — a kernel freeze now costs 30 seconds. And
`fleet/bin/stall-watchdog.py` for the case the hardware cannot see: a box that
answers but never finishes anything. It measures Pressure Stall Information
rather than load, deliberately, because a legitimate ollama run pins all twelve
cores on this GPU-less machine and a load rule would shoot it mid-thought.

**Thresholds are guesses.** `memory full avg60 > 20%`, `io full avg60 > 60%`,
`cpu some avg300 > 90%`, three strikes on a two-minute timer. Reasoned from
first principles, never measured against a real workload. The `cpu some` one is
the weakest and will probably false-positive first. Idle baseline is `0.00`
across the board, which establishes the healthy floor and says nothing about
the ceiling.

**`docs/TRUST-LAYERS.md`.** OPERATOR / TRUSTED / FAMILY / MEDIUM / HOSTILE.
Vocabulary for access rules that already existed in five places without shared
words. FAMILY sits below TRUSTED on purpose: our machines read the open
internet all day, and trust in intent is not trust in judgement.

**Test suite resurrected.** pytest lived only in `.venv311` and died with it.
Once running, every HTTP test failed to *collect* — `starlette` had moved to
`httpx2` while `pyproject.toml` still pinned `httpx`. Fixed; 394 pass.

## Still open

- **The hardware watchdog has never been tested across a reboot.** The config
  is correct on disk. The reboot has not been done. Largest untested
  assumption in the fix.
- **The board still shows stale workers as green.** The NUC failure mode is
  entirely unfixed. This is the highest-value thing left.
- **`localvoice` has been alerting since roughly 10 August** with `qwen2.5:3b
  did not answer (0.0s)`. Nothing remediates it. The council flagged it on at
  least five separate days and nothing happened.
- **Nobody reads the council output.** It correctly diagnosed both the stale
  NUC and the localvoice alert, days before a human noticed either.
- **The Mac has neither watchdog.**
- **Root cause of the freeze is unknown** and probably unknowable from the
  evidence that survived.

## Lessons

1. **A monitor that cannot expire its own answer is not a monitor.** Green
   meant "the last check passed", not "the machine is alive", and those two
   diverged for twelve days.
2. **A frozen machine still draws power**, so restore-on-AC-loss has nothing
   to restore from.
3. **Findings nobody reads are not findings.** The council had this right on
   the 16th.
4. **Tooling that cannot run cannot complain.** A dead pytest hid a broken
   dependency indefinitely.
