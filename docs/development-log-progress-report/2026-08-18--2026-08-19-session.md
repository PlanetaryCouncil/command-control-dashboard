# Session log — 18–19 August 2026

The session that started with "why is the Telegram bot not answering" and ended
with green CI on a repository owned by an organisation.

**26 commits.** 446 tests. Two machines brought level. One nine-day outage
explained, and the fix for it found to be broken before it was ever needed.

---

## What was actually wrong

Three separate silences, each with a different cause, none of them the thing
they looked like.

**The Telegram bot.** Two grey ticks and no reply. Not a broken bot: the
OpenClaw gateway had died at 23:03 the previous night when a config change
triggered a restart that never landed — `Bootstrap failed: 5: Input/output
error`. The service was fully unloaded from launchd, so its own `KeepAlive`
could not save it. Five messages sat queued on Telegram's servers.

**The NUC.** Gone for nine days. It did not crash and it did not shut down; it
**stopped**. The journal ends mid-sentence on 8 August at 19:05 with no
shutdown sequence, and the next boot ran an orphan cleanup. The lesson worth
keeping: **a frozen machine still draws power**, so restore-on-AC-loss has
nothing to restore from. Unplugging it was what finally manufactured the AC
loss the BIOS had been waiting for.

**The board said it was fine the whole time.** `nuc | pass | last_run
2026-08-06` — twelve days green, because a worker that stops reporting keeps
its last status forever. The fleet's own council had spotted it on the 16th and
said so plainly. Nobody was reading the council.

## What got built

**Two watchdogs on the NUC.** The hardware one (`iTCO_wdt`, 30s) for a real
freeze — the only layer that could have caught the 8 August event, since the
thing that would report a freeze is the thing that dies. And a stall watchdog
for the case hardware cannot see: a box that answers but never finishes
anything. It measures Pressure Stall Information rather than load, deliberately
— a legitimate ollama run pins twelve cores here, and a load rule would shoot
the machine mid-thought.

**Then a reboot proved the hardware watchdog had never worked.** Two restarts
came up with no `/dev/watchdog` at all while every config file looked right:
the kernel package deny-lists `iTCO_wdt`, and both `modules-load.d` and the
initramfs silently skip a deny-listed module *while reporting success*. An
explicit `modprobe` in a systemd unit was the fix, confirmed on a third boot.
The assumption flagged as untested was untested for a reason, and it was wrong.

**The board stopped lying.** Staleness now downgrades on every surface rather
than only in the HTML — `/workers.json` had been serving the undowngraded
status, and the JSON is what every agent reads. Two tiers: `warn` past six
hours, `stale` past a day, red and sorted with the failures.

**And it learned to say what it is doing.** `busy` and `thinking`, blue rather
than amber, because a check the fleet deliberately declined to run is not a
failure. Timestamps are labelled `last signal`. A deferral carries the previous
signal forward, so "not now" is fine and "not now for a fortnight" still ages
into red.

**Trust layers.** `docs/TRUST-LAYERS.md` — OPERATOR, VOUCHED, DERIVED, MEDIUM,
HOSTILE. The first draft ranked our own machines below trusted humans and was
corrected: *"Can you make NUC both trusted and family? He is both."* Right, and
the fix was to stop asking one question. Belonging is fixed; authority depends
on where the **words** came from, not who carried them. The NUC is family and
trusted, and a web page it read aloud is still layer 4 afterwards.

**That model then caught a real hole.** Three public endpoints interpolated
visitor-supplied names into `events.jsonl`, and `council.py` feeds the last
sixty events to the agents. An anonymous stranger could write into the context
the fleet reasons from, and `.strip()` left embedded newlines intact, so one
charge could forge a second event beneath itself.

**Charging stayed wide open.** The operator was explicit: let spammers spam,
detect it with dedup. So there is no turnstile — every record carries a salted
hashed hand, and `GET /api/charge` reports unique hands beside raw charges. The
ten rows already on disk made the case: **10 charges, 1 hand**.

**Grok joined the fleet**, registered in all four places onboarding actually
costs, and deliberately without a permission mode: an agent joins able to speak
before it joins able to act.

## The public-release review

Nothing leaks. 191 commits scanned for tokens, keys and private key blocks; the
only hits were the words in documentation. Credentials were kept outside the
tree on purpose and it held. The judging endpoints answer 404 rather than 403,
so a remote caller cannot confirm they exist.

The blockers were all about *receiving* people, not exposing them:

- **CI had never run.** Every run in the repo's history ended in
  `startup_failure` at zero seconds with no jobs created. A trivial three-line
  probe workflow failed identically, which proved it was not the YAML. Moving
  the repository to the PlanetaryCouncil organisation fixed it.
- **`pip install .` had never been able to work** — flat layout, four
  top-level directories, setuptools refusing to guess. CI would have died at
  step two even on a day Actions was willing to start.
- **`.gitignore` covered `.venv/` but not `.venv311/`.** A virtualenv was
  committed once, 2,260 files, with `lib/` tracked and `bin/` not. Restoring
  that from git yields a virtualenv with libraries and no interpreter — which
  is exactly how six fleet services died with `203/EXEC`.

Then CI, on its first real run, immediately caught two tests that only passed
on the machine they were written on.

## Still open

- The Mac has neither watchdog.
- `watchdog.sh` has no load guard and no lock, so a sweep can overlap itself.
  Two ran at once during a load spike that reached **469 on four cores**.
- The NUC does not report to the Mac board, so its card is stale by design.
- Root cause of the freeze is unknown and probably unknowable.
- Python versions disagree: the laptop runs 3.11, the NUC runs 3.14, CI tests
  3.11. The NUC's version cannot be tested — `cffi` has no 3.14 wheel.

## Running lean, and using various models

The subscription came down, so the question changed from *what can this do* to
*what is worth spending on*. Measured rather than guessed:

```
~/.claude/CLAUDE.md                  8,619 bytes
MEMORY.md                            3,029 bytes
prepended to EVERY claude process   ~3k tokens
this session's transcript              3.4 MB
all sessions on disk                   149 MB

rota (hourly)               24 claude calls/day
council (3-hourly)           8
comms-heartbeat (daily)      1
```

**The largest lever is free.** A long session resends its whole history every
turn. Clearing between tasks beats every other optimisation combined, and costs
nothing but the habit.

**The second is cadence.** Hourly rota is 24 invocations a day, each carrying
the full preamble, mostly producing proposals nobody reads that hour.

**The third is the preamble itself.** Three thousand tokens on every
invocation, including all 33 headless fleet calls — and most of that file is
the bar, the sections and the poem, which the file itself says do not apply to
headless agents. Terminal furniture, posted to programs that never render it.

**The fourth is the real structural fix, and it is the reason this matters
beyond money.** The fleet now has five agents: claude, hermes, openclaw, ollama
and grok. Two are cloud, one is local, and they are not interchangeable — but
most of what the fleet asks is not hard. A relay hop that adds one to a number
does not need the most expensive reasoner available; it needs *an* agent that
can count. Routing by difficulty rather than by habit is cheaper **and** better
architecture: it keeps the expensive model for the work that is actually hard,
and it means no single vendor's outage or price change can take the fleet down.

The same principle already appears in the Dreamina work — cheap model for the
boring shot, frontier model for the one that has to be extraordinary. It was
right there and it generalises.

Running lean is not doing less. It is knowing which of the five to ask.
